# AI 对话

## 适用场景

用于角色对话、智能点评、动态剧情、问答和根据用户文本生成结果文案。AI 只负责生成文本；玩法阶段、按钮状态、展示节奏和失败兜底由业务脚本负责。

## 设定生成

不调用旧 LLMChat Workflow，也不要在运行时额外发起一次“生成设定”请求。

当需求包含角色、人设、陪伴式对话、互动主持人、剧情人物或指定说话风格时：

1. 必须读取 [角色设定生成](./角色设定生成.md)。
2. 将用户需求整理成 `character_description`，按照该文件生成完整 Profile。
3. 立即将 Profile 写入项目内独立的 `AIConversationProfile.ts`，不要只保留在当前上下文中。
4. 后续编写玩法脚本前必须读取该文件，并将其作为角色设定和交互设计的单一事实源。
5. 用户回答、分数、线索等运行时变化数据需要在每次互动时单独输入，不能写死在 Profile 中。

不需要角色设定的普通文本生成场景，可以直接根据用户需求编写简洁的 `systemPrompt`。

## Profile 的消费边界

玩法脚本需要从 Profile 消费两类信息：

1. 对话生成配置：角色系统设定、开场白、回复随机性、目标回复长度以及语音/选项模式。能力层会将其中 WF 需要的字段转换为固定协议；玩法脚本不得自行拼接 WF 请求。
2. 本地交互设计：语音识别触发方式、文字展示策略、是否允许打断、音色和语速。这些配置由玩法脚本协调 STT、TTS、UI 和轮次状态，WF 不负责执行。`AIConversation` 的 `interactionMode: 'voice'` 只指定对话输出模式，不会自动播放声音。需要 AI 语音回复时，玩法脚本必须按音频能力的 `TextToSpeech.d.ts` 创建 TTS，并将校验后的最终回复（包括备用回复）传给 `speak()`。在 `onEnd` 或 `onError` 后推进轮次；`RecordEnd` 时停止播报。验收时检查实际 TTS 调用及播报后的状态恢复，不能仅检查 Profile 中存在音色配置。

使用选项对话时，玩法必须准备 2–4 个开场选项，并能解析后续回复中以 `/` 分隔的正文和选项。使用语音对话时，不要为了兼容旧 JSAsset 额外实现选项逻辑。

## 用户输入方式

当前 Agent 玩法不提供键盘自由输入能力。需求中的“文本对话”“持续聊天”“自由对话”表示 AI 使用文字协议理解输入、生成回复并维护上下文，不表示玩家通过输入框或系统键盘发送文字。

- 自由对话固定使用麦克风采集用户说话内容，并通过语音转文字得到本轮 AI 输入；不得规划或实现文本输入框、可编辑消息区、系统键盘或“发送文字”按钮。
- 玩家消息区域可以展示语音识别结果，但只能作为不可编辑的对话记录。
- 选项对话只能使用预先展示的有限选项按钮，不属于自由文字输入。
- `auto_speech` 在 `RecordStart` 后自动进入监听，不要求玩家再次点击或按住麦克风；界面使用一条状态 Text 提示“直接说出问题或猜测”“正在识别”“正在思考”“正在回答”等当前阶段，不把状态提示做成按钮。`push_to_talk` 才显示并启用麦克风按钮。
- AI 请求、回复展示和语音播报期间，两种模式都必须停止或暂停玩家语音识别。回复结束后恢复到各自模式的可输入状态；`RecordEnd` 停止识别。
- 当玩法要求 AI 回复出声时，不能仅设置 `AIConversation` 的 `interactionMode: 'voice'` 或在 Profile 中填写音色；这些配置不会自动播放声音。玩法脚本须按音频能力的 `TextToSpeech.d.ts` 实现播报，将校验后实际展示的最终回复交给 `speak()`，并在播放结束或失败后按玩法状态机推进。明确要求静音、只读，或回复不适合朗读时可省略 TTS，但仍须正常展示回复并推进玩法。
- 验收语音回复时，检查实际播报、播放期间的输入状态、播放结束或失败后的恢复，以及玩法退出时的音频清理；不能只检查配置中是否存在 `voice`。

## 交互实现要求

- 语音对话玩法必须使用显式状态机。`auto_speech` 使用 `listening -> thinking -> responding -> listening`；`push_to_talk` 使用 `idle -> listening -> thinking -> responding -> idle`。识别或请求失败时回到当前模式的可输入状态，不得卡在处理中。
- `idle` 可以接受新输入；`listening` 正在收集用户语音；`thinking` 已停止识别并等待 AI；`responding` 正在展示或播报 AI 回复。
- 只有 `idle` 允许开始新一轮输入。任何 STT、AI 请求或 TTS 失败都必须清理当前轮次并恢复到 `idle`，不能卡在思考或回复状态。
- 存在 TTS 时，`responding` 在语音自然播放结束后才结束；仅展示文字时，在 AI 完成回调后恢复 `idle`。
- 自动识声适合持续对话；按键对讲适合需要明确开始和结束输入的玩法。
- 用户语音转文字、AI 回复文字是否展示属于 UI 决策，不能改变 STT 或 AI 请求本身是否执行。
- 允许打断时，用户开始新一轮输入前需要停止当前 TTS，并防止上一轮回调覆盖新一轮状态。
- 不允许打断时，TTS 播放和 AI 请求期间应禁用输入入口，结束或失败后再恢复。
- 固定开场白直接读取 Profile；不要在运行时再次调用 AI 生成角色设定或开场白。
- 所有请求都必须具有加载态、超时/失败提示、恢复交互和重复触发保护。

具体接口、回调、生命周期和脚本示例统一以 `api/AIConversation.d.ts` 中的注释为准。
